> **补充**：本篇偏「仓库结构 / 生成机制 / 工程链路」。
> 针对**每日产出内容本身**（内容分类、内容规范、展示格式、内容来源的量化统计与逆向推理）
> 的后续研究见 `docs/12-内容规范与逆向研究.md` 与 `reports/corpus-analysis.md`。

> 研究时间：2026-11-04。方法：`git clone` 四个仓库后逐个做源码级只读通读
> （README / 配置 / workflow / 脚本 / 测试 / 产物 / git 信息 / 全库 Grep 统计），
> 并额外做了两批共 47 个候选信息源的 HTTP 可达性实测。
> 研究副本位于 `.research/repos/`，均为 `--depth 1` 浅克隆。

## 0. 研究局限（先声明，避免过度推断）

- 四个仓库本地都是**单提交浅克隆快照**，因此**无法从本地评估真实提交频率与逐日历史**。
  活跃度只能由产物日期跨度推断。
- 三个内容仓库（daily-rss / daily-investor / blogpost）**不含生成代码**，
  凡涉及「抓取逻辑 / prompt 原文 / 模型 / cron」的结论，
  要么来自产物正文的自述，要么来自另一个仓库的旁证，本文件一律标注证据等级。
- docs-feed 依赖上游**完整 git 历史**，本地浅副本不能用于复现其发布时间语义。

## 2. 一条流水线（已验证的单向关系）

```
外部 Agent / Cron（采集 · 选题 · 写作 · 行情；代码不在任何仓库内）
      │ git push
      ▼
┌────────────────── 内容层：纯 Markdown 产物仓库 ──────────────────┐
│ daily-rss   2026/MM/YYYY-MM-DD.md       技术日报（256 篇）        │
│ blogpost    YYYY-MM-DD-slug.md          深度文章（333 篇）        │
│ daily-investor  ideas/ + observations/  投资/创意（361 篇）       │
└──────────────────────────┬──────────────────────────────────────┘
                           │ docs-feed/feed.json 配 source，actions/checkout 单向 pull
                           │ （依赖完整 git 历史 fetch-depth: 0 取 published/updated）
                           ▼
┌────────────────── 聚合层：docs-feed ──────────────────┐
│ eligible() 筛选 → git log 取时间 → Markdown→HTML       │
│ → bleach 白名单消毒 → 相对链接绝对化 → 排序取前 100    │
│ → 全量重建 → 字节比较幂等写入 → .tmp→replace → commit │
└──────────────────────────┬───────────────────────────┘
                           ▼
              订阅层：raw.githubusercontent.com/.../releases.atom
                           ▼
                    RSS / Atom 阅读器
```

**单向性证据**：docs-feed 侧 `feed.json` 明列三个 source；三个上游仓库内检索
`docs-feed|feed.json|releases.atom` **零命中**。这是「通过 GitHub 中间存储解耦」的正常表现，
不是「无关联」。汇总时统一用「A 单向消费 B、B 内无反向引用」句式。

**跨仓库推断（C 级，不可写成事实）**：「daily-rss 采集 → OpenClaw 写作 → blogpost 成文」。
依据仅为同作者、同「小R」署名、同每日节奏，以及 blogpost 的 `ANNOUNCE-2026-02-24-double-release.md:122`
把三仓库并列为配套；daily-rss 侧无直证也无反证。

## 3. daily-rss 详解

### 3.1 定位与规格
README 第 1-3 行：「每日技术 RSS 聚合日报，基于多源信息聚合的增强版技术快报」。
README 18-45 行是一份**隐式 prompt 契约**，规定日报必须包含：

| 板块 | 条数 |
| --- | --- |
| 🔥 核心主题聚合 | 6-8 个主题，每主题 2-3 条，相同主题合并 |
| 🌐 开源社区动态 | GitHub Trending Top 8、HN 热门 Top 5 |
| 🤖 LLM 动态速递 | 10-15 条 |
| 💰 投融资快报 / 🛠️ 开发者工具更新 | 各 3-5 条 |
| 📰 行业深度 / 📊 论文精选 | ≥3 篇 / 2-3 篇 |
| 📅 今日活动预告 / 📊 今日数据概览 | 必填 |
| 💡 编者观察 | 500-600 字 |

硬约束：**所有条目必须包含原文链接**；全中文精编；字数目标 5000-7000 字；
页脚写「由 AI 自动生成 | 06:30 CST | 数据源 20+ RSS」。

### 3.2 数据源（27 源，README + 产物清单交叉比对）
- 核心 RSS 5：Karpathy Curated（youmind）、TLDR AI、The Rundown AI、HN Front、GitHub Trending。
- 深度媒体 6：MIT Tech Review AI、WIRED AI、Ars Technica AI、TechCrunch AI、VentureBeat AI、MarkTechPost。
- 行业/研究 9：HF Blog、AI Business、SiliconANGLE、Ahead of AI、KDnuggets、InfoQ、LangChain Blog、Interconnects、Last Week in AI。
- Newsletter 5（**README 未列，只在 2026-09-21.md:230-236 出现**）：Ben's Bites、Jim Nielsen、Poche、DEX 周刊、Dense Discovery。
- 学术 2：arXiv cs.AI / cs.CL 的 **HTML 列表页**（不是 RSS）。
- 全库 16,430 条链接 / 1,168 个域名；Top：github.com 1987、techcrunch.com 1176、
  huggingface.co 1115、arxiv.org 1083、infoq.com 818、aibusiness.com 733、HN 595、tldr.tech 576。

### 3.3 产物与自观测
`2026/MM/YYYY-MM-DD.md`，331 行的最新一期自述「29 信源、原始约 430 条 → 去重后入选 96 条」
（压缩比 ≈4.5:1），并在「今日数据概览」里写入失效源及原因（429/404/空 feed），
等于把 pipeline 健康度写进产物——这条很值得抄。

### 3.4 缺陷
1. 仓库 257 个文件**全是 .md**，零代码/配置/workflow，生成逻辑全黑盒；
2. README 与产物漂移：写 `archive/`（不存在）、06:30（footer 多为 06:00）、
   GitHub Trending 用已 404 的 `github-trends-atom.vercel.app`（实际改直抓页面/镜像）；
3. 源长期带病只在正文标注，无自动替换/告警/重试；
4. 模板 9 个月至少改版 4 次，无 front-matter、无 JSON，机器不可读；
5. **无自产输出通道**：无 feed / HTML / 邮件 / API；文中给的 RSS 是上游 Karpathy 源，易误导；
6. 源 404 时写「基于多源推断的热门项目」，与真实抓取结果混排，可追溯性下降；
7. 去重键、打分算法、测试全无；缺刊 9 天无补刊记录。

## 4. daily-investor 详解

### 4.1 两条内容流
- `ideas/YYYY-MM-DD-ai-product-ideas.md` 223 篇，每日 07:00 北京生成，数据源偏技术社区
  （HN / HF Blog / GitHub Trending / arXiv / MIT TR / Techmeme / Anthropic / OpenAI）。
- `observations/daily-report-YYYY-MM-DD.md` 91 篇（另有 46 篇早期多格式），
  前一美股交易日 ET 收盘数据，08:00 北京发布；含 0-16 章固定结构、
  RSI(14)/均线/利差/ breadth 等指标、8 维风险矩阵、12 只优先观察股。
  目录存在 4 种格式且同日双份，是 prompt 变更未做数据迁移的痕迹。

### 4.2 数据源与降级
- 行情：Yahoo Finance v8 Chart API / yfinance 1.5.1、腾讯、新浪、东财 kline、CNBC JSON-LD；
  双源/三方交叉核对，恒等式 `SPY×10≈SPX`、`QQQ×41≈NDX`、`IWM×10≈RUT`。
- 宏观：FRED（DGS2/10/30，滞后一日）、CME FedWatch、H.15、Polymarket / Kalshi。
- 新闻：CNBC / Bloomberg / Reuters / MarketWatch RSS + Firecrawl `web_search/web_extract`。
- **降级链（值得抄）**：Firecrawl 402 配额耗尽 → RSS + 直连；FRED 未更新 → 显式标注「2Y 为估算值」；
  CME FedWatch 动态渲染取不到 → 写「暂无可靠数据」；cron 会话被 idle-600s 强杀 → 「反思会话」补录；
  单源值（TradingEconomics）事后修订弃用。

### 4.3 反幻觉审计 pilot（唯一可读程序逻辑）
`.github/workflows/report-evidence-audit.md`（176 行）+ 编译产物 `.lock.yml`（1874 行），
gh-aw v0.89.21 / engine `codex` / `gpt-5.1-codex-mini`，**仅 `workflow_dispatch` 手动触发**、
`staged:true` 只预览不建 issue、md 第 162-163 行明确「尚未启用付费运行」。

- 预打包 Python（md:61-115）：路径白名单、拒绝 symlink/路径穿越、UTF-8 严格、
  ≤150000 B、单行 ≤7000 B、≤24 块 × 8000 B、`L{n}:` 行号前缀、SHA256 + manifest、
  凭据正则拦截（`-----BEGIN PRIVATE KEY-----` / `sk-` / `gh[pousr]_` / `github_pat_`）。
- prompt（md:118-156）：全文视为 untrusted data；禁 shell / GitHub 工具 / 联网 / 改文件 /
  交易 / 排名 / 新建 schedule；逐块读 + exact line coverage；claim ID + 精确行范围；
  区分「事实 / 内部算术 / 显式标注的推断 / 无依据解读」；
  `NO_INDEPENDENT_SOURCE_SNAPSHOTS` → 外部事实一律 `UNVERIFIED`；
  禁止模型知识补洞；`INTERNAL CHECK ONLY` 不等于输入为真；no-findings 也须声明未验证。
- 双 Codex 链路：主 agent + `detection` job 的独立威胁检测 agent；
  `max-turns:40`、`timeout-minutes:15`、daily AI credits 上限 5000、OTEL token 汇总。

### 4.4 缺陷
黑盒化（生成代码/prompt/依赖/README 全无）；目录格式反复变化；纯自由文本无结构化输出；
时间窗口漂移（UTC 00:0x / 08:00 北京 / 14:02 / 04:00）；
审计 pilot 自承无独立证据，但日报却含「仓位 5-6 成 / 操作倾向」等建议，定位冲突；
1874 行 lock.yml + 5 job + 多容器只为手动预览一份报告，对个人系统过重。

## 5. blogpost 详解

### 5.1 定位
`README.md:1-3`「技术文章仓库，由 OpenClaw Agent 自动维护」。
根目录 333 篇 .md（297 篇日期命名 + 36 篇非日期），约 7.93 MB，8.7 个月，
文章自述由「小R」自动生成并经人工审核，部分由 4 个 Specialist Agent 协作（架构→代码→测试→审查）。
**不是写作框架、不是博客引擎、无构建/SSG/Pages**，GitHub 仓库本身即发布载体。

### 5.2 内容组织与模板
- 命名 `YYYY-MM-DD-英文-kebab-slug.md`，**文件名即主键**（日期/排序/去重无需 front-matter）。
- **无 YAML front-matter、无标签字段**；分类靠 `scripts/update_readme.py:57-71` 的
  `categorize_file()` 按文件名关键词硬编码，取第一个命中，否则「其他」。
  缺陷：投资类文章落「其他」，README 分类表 26+259+3+1=289 ≠ 实际 328；
  README 索引 328 条链接 vs 333 篇实际文章；头部「最后更新 2026-11-04 10:50」
  与 footer「自动生成于 2026-09-22 08:06」矛盾。
- 统一文章模板：H1 → 数据化导语 blockquote（170/297 篇前 6 行内）→
  中文编号章节（264/297 用 `## 一、`）→ 表格/ASCII 架构图 → `## 参考资料` → 生成声明；
  104 篇日期文章含「原文来源 / 原文链接」块，系列文章带「上一篇/下一篇」「本仓库相关文章」互链。

### 5.3 最值得抄的一条原则
`docs/translation-fidelity-pilot.md:3` 明写「原有 `scripts/update_readme.py` 保持不变，
**目录工作继续使用确定性脚本**」——统计/分类/排序/索引绝不让 LLM 参与。
另把「写入」与「质检」彻底解耦：译文忠实度审计是只读、有界、staged 的，
输入视为不可信数据，超限报 `INCOMPLETE`，只出报告不改文件。

### 5.4 缺陷
333 篇平铺根目录无归档；索引需手工跑、无 CI 触发；核心采集/写作工作流不在仓库；
`reports/`、`blogpost/images/` 与根目录存在同主题重复文件；图片引用混用 `/tmp/`、
仓库相对路径与 raw 绝对地址；**`finnhub-integration-complete.md:42` 明文硬编码
`FINNHUB_API_KEY`、`:97` 明文记录 GitHub token 的 `credential.helper` 写法**；
质量审计只是试点（无密钥、无 schedule）；无 LICENSE / CONTRIBUTING。

## 6. docs-feed 详解

### 6.1 真实机制（最重要的认知纠正）
README 第 3 行：「把技术日报、技术文章和 AI 产品创意汇总为一个 Atom 1.0 全文订阅源」。
**它不追踪任何官方文档站 / changelog / 规范站点，也不调用 GitHub Releases API**。
`feed.json` 的三个 source 全是作者自己的仓库：

| repository | directory | label | prefix | 附加 exclude |
| --- | --- | --- | --- | --- |
| kejun/daily-rss | daily-rss | 技术日报 | `""`（全库） | — |
| kejun/blogpost | blogpost | 技术文章 | `""` | NEW-REPOS-*.md / PROMOTION-PACKAGE / REPO-SETUP-GUIDE / docs/translation-fidelity-pilot |
| kejun/daily-investor | daily-investor | AI 产品创意 | `ideas/` | — |

实测 `releases.atom` 100 条：blogpost 41、daily-investor ideas 30、daily-rss 29。

### 6.2 变更检测与增量更新
- **不做内容 diff**：`scripts/generate_feed.py:57-89` 用
  `git log --format=%x1e%ct --name-only -z --no-renames --diff-filter=AMT HEAD`
  遍历完整提交历史，取每文件首次提交时间作 `published`、末次作 `updated`（`%ct` committer epoch）。
  好处：定时检查本身不改变订阅时间，阅读器不误报；编辑保留相同 ID。
  代价：**必须 `fetch-depth: 0`**，shallow 或脏工作区直接抛错（:59-62）。
- **「增量」= 全量确定性重建 + 幂等写入**：排序 `(-updated, repository, path)` 带确定性 tie-break、
  白名单消毒、`xml_text` 清控制字符 → 内容不变则字节不变 →
  `:205` `read_bytes()==content` 跳过写入 → `:208-210` `.tmp→replace` 原子替换 →
  `publish_feed.py:34` `git diff --cached --quiet` 决定不提交。
- 发布安全：`publish_feed.py:21-49` 发布前刷新三源到最新 base、push 竞态最多 3 次重试；
  Actions `concurrency` 组；PR / 非 main 只生成不发布；13 个单测覆盖确定性、失败保留旧产物等。
- 渲染：Markdown → `tables/fenced_code/sane_lists` → `bleach.clean` 白名单 →
  `FeedHTML` 把相对链接/图片 `urljoin` 成 GitHub / raw 绝对地址 → 首个 `<h1>` 作标题 →
  纯文本前 300 字作 summary。实测产物 `<script`/`onerror=`/`javascript:` 残留均为 0。

### 6.3 缺陷
1. 名不副实（名字与产物 `releases.atom` 极易误导，README 第 7 行专门澄清
   **不能用 GitHub 仓库页自动生成的 `/releases.atom`**）；
2. 每次遍历三源完整 git 历史并重渲染 100 篇全文，3.9MB 单文件每日全量重写提交，仓库线性膨胀；
3. 100 条硬截断 + **无历史留存 / 无归档**；无「仅新增项」通知能力；
4. 只有 3 个来源级 category，无主题分类、无去重逻辑、无内容级 diff；
5. summary 是机械截断（可能在词中断开），标题依赖首个 h1；**完全无 LLM**；
6. URL 硬编码 `main`；单一产物、被动订阅，无邮件 / API / webhook / 告警；
7. `--no-renames` 使重命名 = 删旧 + 新增，阅读器可能重复收录；
8. GitHub Actions schedule 连续 60 天无活动可能被停用，且 cron 排队可能延迟；
9. **安全闸门缺失**：`bleach` 只做标签白名单，不扫正文密钥（见下节）。

## 7. 交叉校验修正（汇总以此为准）

1. **docs-feed 真实职责** = 聚合自有仓库 Markdown → 全文 Atom，不是官方文档变更监控。
2. **blogpost → docs-feed 单向**：blogpost 是产量最大的来源（41/100）；
   其「本地 `/tmp/` 图片 → raw 绝对地址」的发布前替换，正是为适配下游聚合的 `urljoin`。
   首个 `<h1>` 取标题、300 字摘要正好吃到模板的数据化导语 blockquote，两侧解析约定同源。
3. **`prefix:""` 理论全库收录 vs 实际未出现元文档**：`max_entries=100` + `updated` 倒序截断，
   使 41 条 blogpost 全是 2026-09-30 之后的日期命名文章。
4. **密钥扩散风险（条件触发，尚未实际泄漏）**：`finnhub-integration-complete.md`
   明文含 API Key 与 GitHub token 写法，且不在 blogpost 专属排除清单里；
   用与 `eligible()` 一致的逻辑复刻判定，该文件及 `ANNOUNCE-*`、
   `automation-tools-comparison.md` 等 6 个元文档均会被判为 IN。
   当前 `releases.atom` 全量 grep 相关关键词 **0 命中**——一旦这些文档被编辑刷新 `updated`、
   调大 `max_entries` 或源文档减少，就会被全文收进公开 Atom。
   建议改「黑名单 exclude」为「仅允许日期命名文章」的 include 策略，或加凭据扫描。
   → 本方案已在三处落地扫描。
5. **日期口径差异**：blogpost 从文件名解析日期（36 篇非日期文件回退 git log 或写死 `"2026-02"`），
   docs-feed 一律用 git 提交历史；feed 级 `<updated>2026-11-04T03:26:49Z</updated>`
   与 blogpost 本地唯一提交 `5007e34 | 11:26:49 +0800` 完全一致，实证「取排序后最新文档末次提交时间」。
6. **浅克隆冲突**：聚合层要求完整历史；本地四个研究副本均为单提交快照，
   不能用来评估活跃度，也不能直接喂给聚合层。
7. **抓取策略不可混用**：daily-rss 以 RSS 为主（27 源，失效换源/HTML/API 近似）；
   daily-investor 以 Firecrawl / 行情 API 为主（RSS 是 402 额度耗尽后的兜底）+ 多源恒等式核对。
   daily-rss 的 arXiv 是 HTML 列表页而非 RSS；X/Twitter 在 daily-rss 是正文引用链接（x.com 120 次）
   **不是订阅源**；Product Hunt / Techmeme 不在 daily-rss 源清单（Techmeme 属 daily-investor ideas 流）。
8. **daily-rss 与 docs-feed 的两层结构**（内容层纯 md + Git → 聚合层 Atom）比
   「订阅只能看 GitHub 仓库」更完整，是本方案推荐的输出架构，但须补历史留存与安全闸门。

## 8. 证据强度分级

| 级别 | 含义 | 典型例子 |
| --- | --- | --- |
| **A · 直证** | 仓库内代码 / 配置 / workflow / 产物可复核 | `feed.json` sources；`generate_feed.py:57-89`；`update_readme.py`；本次 47 个信源 HTTP 实测 |
| **B · 产物自述** | 生成日报的 AI 写入正文，无源码佐证 | 27 源清单、430→96 去重比、OpenClaw Cron 时间、Firecrawl 402 降级、反思会话补录 |
| **C · 跨仓库推断** | 同作者 / 同署名 / 同节奏的合理推断，无双向直证 | daily-rss → 写作 → blogpost；外部 Agent 的具体模型与编排 |

汇总中所有 C 级结论必须写「推断」，不得写成已验证 pipeline。
