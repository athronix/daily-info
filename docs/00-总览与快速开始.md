# 00 · 总览与快速开始

> 目标：用 WorkBuddy 给自己搭一套**每日信息挖掘 → 分类聚合 → 分析总结 → 综合展示 → 订阅分发**
> 的任务 / 服务 / 网站。方案基于对 `kejun/daily-rss`、`daily-investor`、`blogpost`、`docs-feed`
> 四个仓库的源码级深度研究，并已落地为可运行的配置、脚本、prompt、skill、模板与站点原型。

## 1. 一句话方案

**以 `digest.json` 为唯一事实源**：确定性脚本负责采集、归一、去重、打分、索引与全部对外产物；
生成式模型只负责主题命名、解读与编者观察，且被 id/url 白名单锁死，不能新增任何事实。
每天由 WorkBuddy 定时任务驱动，产出静态站 + 5 个 Atom 订阅源 + JSON Feed + 邮件 +
企业微信简报 + 资料库沉淀，并在分发前跑独立核验闸门。

```
信源 → 原始快照 → 归一 Item → 去重聚类打分 → 候选集(prompt-input)
   → [AI 边界] ai-review.json → digest.json(唯一事实源)
   → 站点 / Atom / JSON Feed / 邮件 / 企微 / 资料库 → verify 闸门 → 分发
```

## 2. 为什么这样设计（四仓库研究给出的三条硬结论）

1. **「只有成品、没有工厂」是最大的坑**：daily-rss / daily-investor / blogpost 三个仓库
   分别累计 256 / 361 / 333 篇内容，但**仓库内零生成代码**，采集、去重、prompt、cron 全在外部 Agent，
   不可复现、不可迁移。→ 本方案把全部规则层脚本与配置入库。
2. **确定性脚本做索引、生成式模型只做内容**（blogpost 明文原则）：
   统计/分类/排序/feed 生成绝不让 LLM 参与，保证可复现、零成本、可 diff。
3. **内容层与订阅层必须解耦**（daily-rss → docs-feed 两层结构）：
   内容仓库只写 Markdown + Git，聚合层单独做 feed；本方案进一步用 digest.json 做统一事实源，
   订阅层全量确定性重建 + 幂等写入，补上 docs-feed 缺失的历史留存、多 feed 与安全闸门。
4. **内容质量要变成程序闸门，而不是提示词里的愿望**（见 `docs/12`）：
   三仓库语料实测 100% 产物有「加粗判断句 + 列表 + 原文链接」，含数字的行占 20.8%–48.7%，
   投资日报 53.3% 的文件真的写了「暂无可靠数据」，每期都给可证伪阈值。
   本方案据此把每条内容锁成**七要素**（事实锚点 / 数字 / 实体 / 佐证 / 为什么 / 对我意味着什么 /
   下一步动作），且数字、实体、链接必须能在原文中逐项找到，否则丢弃并告警；V8 核验达标率。
