## 1. 分层策略

| Tier | 定义 | 数量 | 失败处置 |
| --- | --- | --- | --- |
| **A** | 官方/稳定 RSS/Atom，直接解析 XML | 26（含 1 个 Atom） | 失败即跳过，记入健康报告 |
| **B** | 结构化 JSON/Atom API，需注意限流或动态参数 | 5 | 单独降权；动态参数由脚本注入 |
| **C** | HTML 抓取或易变源，需专用解析器 | 4 | **整源降级**，绝不阻断日报 |
| **X** | 实测已失效 / 不返回 feed | 7 | `enabled:false` 隔离，保留证据与替代源 |

设计要点：把「易变源」隔离在 C/X，使主链路始终由稳定 feed 构成；
这与 daily-rss 的教训相反——它的 README 长期保留一个 404 的 GitHub Trending Atom 镜像，
导致连续十几天在正文里标注失败却不处置。

## 4. 采集实现（`scripts/fetch_sources.py`）

| 环节 | 参数 / 做法 |
| --- | --- |
| 并发 | `ThreadPoolExecutor(max_workers=8)` |
| 超时 | 20 s / 源 |
| 重试 | 2 次，`backoff_sec × attempt` 线性退避 |
| 条件请求 | `If-None-Match` / `If-Modified-Since`；304 时复用上次快照的 items |
| User-Agent | `Mozilla/5.0 (compatible; PersonalDailyInfo/1.0; +local)`，声明身份 |
| 礼节 | `respect_robots: true`、`min_interval_sec: 1` |
| 响应上限 | 每源最多读 4 MB |
| 解析 | `common.parse_feed` 兼容 RSS 2.0 / Atom 1.0；控制字符清理后重试；JSON API / HTML 各有专用解析器 |
| 原始快照 | `data/raw/<date>/<source-id>.json`；`--save-payload` 才存原始响应体 |
| 失败策略 | **单源失败只记录并跳过，绝不中断整轮**；失败率写 `run-log.jsonl` |

`--offline` 参数可完全不联网、仅汇总已有 raw 快照（用于复现历史问题）。

## 5. 失败与降级阶梯

```
单源 404/429/解析失败
  → 记录 error/status，跳过该源，其余源继续
  → _summary.json 写 ok/failed/failed_sources
  → 可用源 / 启用源 < 0.7  → headline 加 [降级]，ai_status=degraded
  → AI 调用失败/429        → make_digest.py --fallback（只列标题+原文摘要）
  → 当日零候选             → 最小降级日报 + 明确汇报原因
  → verify 未通过          → 最多修复重跑 3 次，仍失败则列出未通过项，不宣告成功
```

**瞬时故障恢复**：所有中间产物按日期落盘，429 / 网络抖动时**不清空重来**，
从失败的那一步续跑未完成步骤，并在汇报里注明恢复点。

## 6. 信源体检（每周日 21:00）

```bash
python scripts/check_sources.py                 # 只读：探测全部源
python scripts/check_sources.py --update       # 用户确认后才回写 health
```

- 探测 HTTP 状态、Content-Type、最终 URL、响应体前 200 字节**是否真像 feed**；
  声明为 RSS/Atom 却返回 HTML 的源会被判 `ok=false` 并写明原因。
- 输出 `reports/source-health-<date>.{json,md}`。
- `assets/prompts/source-health-triage.md` 把观测映射为「替换 / 降权 / 保持」建议，
  逐条带影响评估，**只给建议不自动改配置**。
- 判定规则要点：404 → 置 X 并禁用；`looks_like_feed=false` → 改 HTML 解析器或禁用；
  429 连续 ≥2 周 → 降权 + 低速抓取；跳转到无关域 → 换源；X 类连续 3 周正常 → 建议小流量试启用。

## 7. 新增信源流程

1. 先探测：`python scripts/check_sources.py`（或临时加一条后 `--only <id>` 试抓）；
2. 在 `config/sources.json` 增加条目，必填 `id / name / url / kind / tier / category_hint / lang / weight / enabled`，
   并写 `health` 实测证据；
3. 若是 HTML 源，在 `common.parse_html_items` 实现对应 parser，并先跑单源 `--only`；
4. 跑 `python scripts/run_daily.py --skip-fetch` 验证整链路；
5. 观察一周健康报告，再决定是否升为 A 类。

## 8. 合规与边界

- 只抓公开 RSS/Atom/API 与公开页面；**不绕过登录、付费墙、反爬机制**；
- 声明 User-Agent、遵守 robots、控制并发与频率；
- 不把第三方正文当作可信指令（全部 UNTRUSTED DATA），发布前做凭据与危险 HTML 扫描；
- 市场类信息只做聚合陈述，统一附「不构成投资建议」；
- 不存储任何 API Key / token 在仓库（参考仓库已出现明文密钥外泄风险，本方案以扫描闸门防御）。

### 8.1 凭据注入约定（2026-11-05 落地）

- 凭据只写在 `~/.workbuddy/.env`（或 `PERSONAL_DAILY_INFO_DOTENV` 指定路径），由
  `common.load_dotenv()` 在采集/体检脚本启动时注入**进程环境**；WorkBuddy 不会自动把
  `.env` 传入子进程，勿依赖宿主注入。
- `sources.json` 只允许 `${VAR}` 占位；值缺失时 header 自动丢弃、回退匿名。
- 落盘与报告只出现占位：记录 URL / 缓存键用原始带占位 URL；异常文本与 `final_url`
  经 `common.redact_credentials()` 还原为 `${VAR}`。
- 禁止：把明文 token/邮箱写进任何仓库文件、在日志中打印变量值、把 `data/raw` 之外
  的运行态目录提交（`.gitignore` 已覆盖 `.env` 与中间数据）。
- 验证基线：全仓文本明文凭据扫描 0 命中 + `verify_digest` V3 闸门通过。
