# 02 · 总体架构与信息流

> **v2 更新（2026-11-04）**：新增 `config/content-spec.json`（七要素内容规范）与
> `scripts/analyze_corpus.py`（三仓库语料量化研究，产出 `reports/corpus-analysis.*`）。
> 合成层 `make_digest.py` 增加数字/实体/佐证 URL 的原文白名单校验，核验增加 V8 内容丰富度。

## 1. 设计目标与约束

| 目标 | 约束 / 取舍 |
| --- | --- |
| 每日自动出报 | 调度用 WorkBuddy 定时任务，不依赖 GitHub Actions schedule（避免 60 天无活动停用） |
| 可复现、可迁移 | 全部规则层代码与配置入库；零第三方依赖（仅 Python 标准库） |
| 可离线排障 | 原始快照按日期落盘，`--skip-fetch` 可重放；`--offline-demo` 可全链路 smoke |
| 内容可信 | AI 被 id/url 白名单锁死；不编造事实；外部事实统一标注未独立验证 |
| 多端可达 | 静态站 + Atom + JSON Feed + 邮件 + 企微 + 资料库，全部从同一事实源投影 |
| 零运维 / 零托管成本 | 静态文件 + Git + 资料库，无数据库服务、无后端进程 |
| 长期可维护 | 配置驱动信源、单一时间口径、结构化 schema、发布前核验闸门 |

**明确不做**：不自研反爬绕过；不抓取需登录/付费内容；不做实时行情交易系统；
不把 LLM 用于统计、索引、去重判定；不把中间层（raw/normalized/candidate）发布出去。

## 2. 分层架构

```
┌─ 调度层 ──────────────────────────────────────────────────────────┐
│ WorkBuddy Automation：每日 06:45 / 周一 08:30 / 周日 21:00 / 月初 09:00 │
│ 绑定 @skill:daily-info · agent-mail · 资料库 · 企微推送（可选）        │
└───────────────────────────┬───────────────────────────────────────┘
                            ▼
┌─ 信源层 ──────────────────────────────────────────────────────────┐
│ config/sources.json：Tier A 稳定 feed / B 结构化 API / C HTML / X 失效│
│ 45+ 源（含中英文、Releases Atom、HN Algolia、arXiv API、HTML 列表）   │
└───────────────────────────┬───────────────────────────────────────┘
                            ▼ fetch_sources.py（并发 8 / 超时 20s / 重试 2 / ETag）
┌─ 数据采集层 ──────────────────────────────────────────────────────┐
│ data/raw/<date>/<source-id>.json   可重放快照 + _summary.json        │

┌─ 研判层 ──────────────────────────────────────────────────────────┐
│ data/digest/<date>/ai-review.json（严格 JSON Schema）                │
│ 只做：主题命名 / 编排 / why_matters / 编者观察 / 短简报              │
└───────────────────────────┬───────────────────────────────────────┘

┌─ 唯一事实源 ──────────────────────────────────────────────────────┐
│ data/digest/<date>/digest.json  ← 站点/订阅/邮件/企微/资料库全部投影 │

┌─ 服务层 ──────────────────────────────────────────────────────────┐
```

## 3. 组件清单与职责

| 组件 | 输入 | 输出 | 关键性质 |
| --- | --- | --- | --- |
| `common.py` | — | 共享工具 | 标准库 RSS/Atom/JSON/HTML 解析、URL 归一、幂等写、日志 |
| `check_sources.py` | sources.json | `reports/source-health-*` | 每周体检；`--update` 才回写健康状态 |
| `fetch_sources.py` | sources.json | `data/raw/<date>/` | 并发、退避、条件请求、**单源失败不中断整轮** |
| `normalize.py` | raw | `items.jsonl` + seen.db | 时间窗、canonical_url、规则分类、跨天去重 |
| `dedupe_cluster.py` | items | clusters + prompt-input | 并查集聚类、6 维打分、配额选择 |
| `make_digest.py` | clusters + ai-review | **digest.json** + md + brief | 白名单过滤、凭据扫描、降级出报 |
| `build_feeds.py` | 全部 digest | Atom ×5 + feed.json | 稳定 ID、幂等、消毒、发布闸门 |
| `build_site.py` | 全部 digest | index/latest/<date>.json | 静态切片、幂等 |
| `verify_digest.py` | 所有产物 | `reports/verify-*` | V1~V8 独立核验 |
| `pack_week.py` | 7 天 digest | `week-<ISO>.json` | 周复盘输入裁剪 |
| `retention.py` | 中间层目录 | 留存报告 | 默认 dry-run，`--apply` 需确认 |
| `run_daily.py` | — | 编排 | 串联 7 步；`--offline-demo` 全链路 smoke |

## 4. 关键设计决策

### D1 · AI 边界放在候选集之后
`dedupe_cluster.py` 已经把「哪些条目值得看」用确定性规则决定完，
AI 只拿到精简后的 `prompt-input.json`（每簇 ≤8 条、字段截断、约 1–3k tokens/天）。
好处：成本可控、结果可复现、AI 无法「顺手加一条新闻」、可离线重放。
对照参考仓库：daily-rss 把去重与排序全交给 LLM，压缩比 4.5:1 但无算法可审计。

### D2 · 唯一事实源 digest.json
站点、5 个 Atom、JSON Feed、邮件、企微、资料库**全部从同一个 JSON 投影**，
禁止各通道另写一份内容。这样「改数据不改代码」，且核验只需验一份事实源 + 投影一致性。
对照：docs-feed 只有单一 atom 产物，daily-rss 只有 md，都没有机器可读事实源。

### D3 · 全量确定性重建 + 幂等写入
所有产物每次全量重建；`write_json` / `write_bytes_idempotent` 先字节比较，
不变则不落盘；写入用 `.tmp → replace` 原子替换。
好处：无状态、可复现、内容不变不触发发布、天然防重复推送。
核验 V5 通过「二次构建 + 哈希比对」实证这一点。

### D4 · 发布前安全闸门
三处凭据正则扫描（make_digest / build_feeds / verify_digest），
命中即拒发并保留旧产物；HTML 只用自建固定标签 + 全量 `html.escape`。
直接针对参考仓库暴露的「公开 Atom 二次扩散明文密钥」风险。

### D5 · 降级优先于空跑
单源失败 → 记录跳过；可用源 < 70% → 降级标记；
AI 缺失/429 → 纯规则降级出报；零候选 → 最小日报。
**宁可出一份标注降级的薄报，也不假装成功或空跑。**

### D6 · 单一时间口径
`published_at` 统一 UTC ISO8601(Z)；业务 `date` 用 Asia/Shanghai 自然日；
`generated_at` 用 UTC。文件名/文内日期只作展示，不参与排序与去重。
对照：参考仓库存在文件名日期、文内日期、git 提交时间三套口径。

## 5. 技术选型与理由

| 选择 | 理由 |
| --- | --- |
| Python 3 标准库（不装依赖） | 定时任务零安装；urllib + ElementTree + HTMLParser 足够解析 RSS/Atom/JSON/HTML |
| SQLite (`seen.db`) | 只需一张表做跨天去重与 novelty；无需数据库服务 |
| JSONL 中间层 + JSON 事实源 | 可 diff、可流式读、可被任意语言消费；比纯 Markdown 机器可读 |
| 静态单页 HTML + 原生 JS | 无构建、无 CDN、无后端；发布为网站即用 |
| Atom 1.0 全文 + JSON Feed 1.1 | 兼容所有 RSS 阅读器；JSON Feed 便于程序消费并带扩展字段 |
| WorkBuddy Automation | 原生支持技能/连接器/企微推送/运行记录，不依赖 CI cron |
| 资料库 + Git 双沉淀 | 资料库跨设备可检索；Git 提供版本与可 diff 历史 |

**未选**：向量库 / 全文检索服务（每日几十条，前端过滤足够）；
MinHash LSH（>5000 条/日再引入，见 `04`）；SSR 框架（静态 JSON 已足够）；
Firecrawl / 付费抓取（个人系统成本敏感，RSS + 官方 API 优先）。

## 6. 容量与性能估算（按每日 30–40 源、300–500 原始条目）

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 采集耗时 | 10–30 s | 并发 8、超时 20s、失败源退避 |
| 归一 + 聚类 | < 5 s | O(n²) Jaccard，500 条约 12.5 万次比较，纯内存 |
| AI 输入 | 1–3k tokens/天 | 40 簇 × ≤8 条 × 截断字段 |
| digest.json | 30–80 KB/天 | 永久保留，一年约 15–30 MB |
| raw 快照 | 0.5–3 MB/天 | 保留 30 天，约 15–90 MB |
| feed | ≤100 条 × 5 profile | 每个 atom 约 100–300 KB |
| 站点数据 | 每日期一个 JSON | 归档索引只存 headline + stats，很轻 |

> 上述为**估算**，不是实测；真实值取决于当日信源返回条目数与失败率。
> 实测值以 `data/raw/<date>/_summary.json` 与 `digest.stats` 为准。

## 7. 扩展点

| 需求 | 扩展方式 |
| --- | --- |
| 增加信源 | 只改 `config/sources.json`；HTML 源需在 `common.parse_html_items` 加解析器 |
| 增加分类 | 只改 `config/taxonomy.json` 的 categories 与 keywords |
| 增加订阅维度 | 在 `subscriptions.json` 的 profiles 加一条过滤表达式（`build_feeds.match_filter` 已支持 4 类表达式） |
| 换 LLM / 换 Agent | 只替换「写回 ai-review.json」的环节，规则层不动 |
| 多机部署 | 同一 WorkBuddy 账户下用资料库同步产物；skills 用 symlink 共享（本机约定） |
| 事实核查增强 | 增加独立来源快照采集器后，把 `evidence-audit.md` 的状态从 UNVERIFIED 升级 |
| 大规模条目 | `dedupe_cluster.py` 的 O(n²) 换 MinHash LSH（代码注释已标注位置） |
